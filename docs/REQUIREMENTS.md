# Requirements: AI Tasks Orchestrator

## Обзор

Спецификация описывает требования к MVP платформы AI Tasks Orchestrator на основе сценариев из MVP Scope. Платформа позволяет техлиду управлять полным циклом разработки через AI-агентов: от дизайна до PR. Требования охватывают управление проектами, задачами, взаимодействие с агентом, параллельную реализацию и интеграцию с GitHub.

## Функциональные требования

### FR-1: Управление проектами

| ID | Требование | Приоритет |
|---|---|---|
| FR-1.1 | Система должна позволять создавать проект с обязательным названием (3-200 символов) и ссылкой на GitHub-репозиторий | Must |
| FR-1.2 | Система должна позволять указывать опциональное описание проекта | Should |
| FR-1.3 | Система должна принимать GitHub Personal Access Token для доступа к репозиторию при создании проекта | Must |
| FR-1.4 | Система должна отображать список всех проектов пользователя | Must |
| FR-1.5 | Система должна позволять входить в проект для работы с его задачами | Must |
| FR-1.6 | Дубликаты названий проектов допустимы | Must |

### FR-2: Создание дизайна задачи

**Связанный сценарий:** Сценарий 1

| ID | Требование | Приоритет |
|---|---|---|
| FR-2.1 | Система должна позволять создавать задачу с обязательным названием (3-200 символов) внутри проекта | Must |
| FR-2.2 | После создания задачи система должна открывать чат с агентом | Must |
| FR-2.3 | Агент должен вести пользователя по структурированному скиллу — вопрос за вопросом с вариантами ответов | Must |
| FR-2.4 | Пользователь должен иметь возможность отклониться в свободный диалог и вернуться к структуре | Must |
| FR-2.5 | Агент должен формировать дизайн-документ в формате Markdown по итогам диалога | Must |
| FR-2.6 | Система должна отображать дизайн-документ для просмотра | Must |
| FR-2.7 | Пользователь должен иметь возможность запросить правки дизайна через чат | Must |
| FR-2.8 | Система должна хранить только актуальную версию дизайн-документа | Must |
| FR-2.9 | Пользователь должен иметь возможность утвердить дизайн — задача переходит на стадию "План" | Must |

| FR-2.11 | Дубликаты названий задач внутри проекта допустимы | Must |

### FR-3: Генерация плана реализации

**Связанный сценарий:** Сценарий 2

| ID | Требование | Приоритет |
|---|---|---|
| FR-3.1 | Система должна позволять генерировать план из утверждённого дизайна по команде пользователя | Must |
| FR-3.2 | Агент должен анализировать дизайн-документ и исходники проекта при генерации плана | Must |
| FR-3.3 | План должен состоять из текстовых шагов с зависимостями между ними (граф) | Must |
| FR-3.4 | Агент должен предупреждать в чате, если шаги зависят от нереализованных задач | Must |
| FR-3.5 | Агент может отказаться генерировать план, если дизайн-документ недостаточно проработан | Must |
| FR-3.6 | Пользователь должен иметь возможность запросить правки плана через чат | Must |
| FR-3.7 | Пользователь должен иметь возможность утвердить план — задача переходит на стадию "Реализация" | Must |
| FR-3.8 | Пользователь должен иметь возможность вернуть утверждённый план на доработку, если реализация ещё не началась | Must |
| FR-3.9 | После начала реализации план не может быть изменён | Must |

### FR-4: Параллельная реализация агентами

**Связанный сценарий:** Сценарий 3

| ID | Требование | Приоритет |
|---|---|---|
| FR-4.1 | После утверждения плана система должна автоматически запустить реализацию | Must |
| FR-4.2 | Система должна распределять шаги по агентам согласно графу зависимостей | Must |
| FR-4.3 | Независимые шаги должны выполняться параллельно | Must |
| FR-4.4 | Агенты должны коммитить код в репозиторий проекта | Must |
| FR-4.5 | Агенты должны прогонять тесты после коммита | Must |
| FR-4.6 | Агенты должны проводить взаимное ревью кода | Must |
| FR-4.7 | Результаты ревью (комментарии, запрошенные исправления) должны отображаться в интерфейсе как артефакты | Must |
| FR-4.8 | Прогресс выполнения должен отображаться через чекбоксы в плане | Must |
| FR-4.9 | Пользователь должен иметь возможность писать комментарии/указания агенту в чате во время реализации | Must |
| FR-4.10 | Пользователь должен иметь возможность остановить всю реализацию целиком | Must |
| FR-4.11 | При неудаче агент должен попытаться решить проблему самостоятельно | Must |
| FR-4.12 | Если агент не смог решить проблему — он приостанавливает текущий шаг, продолжает другие независимые шаги и эскалирует пользователю через чат | Must |
| FR-4.13 | Когда все шаги завершены — задача должна автоматически перейти на стадию "Ревью" | Must |

### FR-5: PR и ревью

**Связанный сценарий:** Сценарий 4

| ID | Требование | Приоритет |
|---|---|---|
| FR-5.1 | После завершения всех шагов реализации система должна автоматически открыть PR на GitHub | Must |
| FR-5.2 | Ссылка на PR должна отображаться в карточке задачи на дашборде | Must |
| FR-5.3 | Агент должен реагировать только на комментарии в PR, содержащие определённый тег (например, `@drim-agent`) | Must |
| FR-5.4 | Агент должен вносить правки по комментариям отдельными коммитами | Must |
| FR-5.5 | Система должна получать уведомления о мёрже PR через GitHub-вебхук | Must |
| FR-5.6 | После мёржа PR задача должна автоматически перейти в стадию "Готово" | Must |

### FR-6: Дашборд

**Связанный сценарий:** Сценарий 5

| ID | Требование | Приоритет |
|---|---|---|
| FR-6.1 | Система должна отображать канбан-доску с колонками: Дизайн, План, Реализация, Ревью, Готово | Must |
| FR-6.2 | Карточки задач должны отображать название и краткий статус | Must |

| FR-6.5 | Дашборд должен обновляться в реалтайме (WebSocket / SSE) при изменении статусов задач и шагов | Must |
| FR-6.6 | Система должна логировать переходы задач между стадиями с датой | Must |

| ID | Требование | Приоритет |
|---|---|---|
| FR-9.1 | Система должна поддерживать вход через OAuth 2.0: Google, GitHub, GitLab | Must |

## Ограничения и допущения

**Ограничения:**

- Правки дизайн-документа только через чат с агентом, без визуального редактора
- Один фиксированный скилл для дизайна (без создания пользовательских скиллов)
- Документы в формате Markdown, без rich-форматирования
- Без поиска, фильтрации и пагинации на дашборде
- Без возможности приостановить/перезапустить отдельный шаг реализации
- Только GitHub (без GitLab для интеграции с репозиториями)
- Без офлайн-режима и PWA
- Однопользовательская система (без командной работы)

**Допущения:**

- Claude Code CLI поддерживает headless-режим, достаточный для автоматизации
- Подписка Claude Max покрывает нагрузку до 10 параллельных задач
- Пользователь имеет права на запись в подключаемый GitHub-репозиторий
- Количество задач на дашборде не превысит 20-30 в рамках MVP

## Зависимости между требованиями

Рекомендуемый порядок реализации:

1. **Аутентификация (FR-9)** — базовая инфраструктура, без неё нет доступа
2. **Проекты (FR-1)** — контейнер для задач, нужен до создания задач
3. **Чат-инфраструктура (FR-8)** — нужна для дизайна, плана и эскалаций
4. **Дашборд (FR-6)** — нужен рано для навигации между проектами и задачами
5. **Создание дизайна (FR-2)** — зависит от проектов + чата
6. **Генерация плана (FR-3)** — зависит от дизайна
7. **Реалтайм-обновления (FR-6.5)** — нужны для дашборда и реализации
8. **Параллельная реализация (FR-4)** — зависит от плана + реалтайм + интеграция с Claude Code CLI
9. **PR и ревью (FR-5)** — зависит от реализации + GitHub-вебхуки
10. **Полировка адаптивного интерфейса (FR-7)** — сквозной, применяется с первого дня, полируется в конце

## Глоссарий

| Термин | Определение |
|---|---|
| Задача (Task) | Единица работы верхнего уровня. Проходит стадии: Дизайн → План → Реализация → Ревью → Готово |
| Шаг (Step) | Элемент плана реализации внутри задачи. Выполняется агентом |
| Проект (Project) | Контейнер для задач, привязанный к GitHub-репозиторию |
| Дизайн-документ | Markdown-документ, описывающий что и как нужно реализовать, сформированный в диалоге с агентом |
| План | Список шагов с зависимостями, сгенерированный агентом из дизайн-документа |
| Скилл | Структурированный сценарий диалога агента с пользователем (вопрос за вопросом) |
| PAT | Personal Access Token — токен для доступа к GitHub API |
| Эскалация | Ситуация, когда агент не может решить проблему и запрашивает помощь пользователя |
