# MVP Scope: AI Tasks Orchestrator

## Обзор

Адаптивное веб-приложение для управления полным циклом разработки через AI-агентов (Claude Code). Пользователь создаёт задачи, проходит стадии дизайна, планирования и реализации в диалоге с агентом, а система автоматически оркестрирует параллельную работу агентов, коммиты, тесты и взаимное ревью. Ключевая ценность — параллельность (несколько задач на разных стадиях одновременно) и мобильность (работа с любого устройства, персистентность контекста между сессиями).

## Терминология

- **Задача (Task)** — единица работы на верхнем уровне. Проходит стадии: Дизайн → План → Реализация → Ревью → Готово. Может быть новым модулем, доработкой, рефакторингом.
- **Шаг (Step)** — элемент плана реализации внутри задачи. Выполняется агентом. Пользователь видит прогресс через чекбоксы, но не управляет шагами напрямую.

## Пользовательские сценарии

### Сценарий 1: Создание дизайна задачи

**Приоритет:** Критичный

**Описание:** Пользователь хочет проработать изменение (новый модуль, доработка, рефакторинг) в структурированном диалоге с агентом.

**Основной поток:**

1. Пользователь нажимает "Создать задачу" на дашборде
2. Открывается чат с агентом
3. Агент ведёт по структурированному скиллу — вопрос за вопросом с вариантами ответов
4. Пользователь может отклониться в свободный диалог и вернуться к структуре
5. Агент формирует Markdown-документ дизайна
6. Пользователь просматривает документ и просит правки через чат
7. Пользователь утверждает дизайн — задача переходит на стадию "План"

**Альтернативные пути:**

- Пользователь закрывает браузер на середине — при возвращении диалог продолжается с того же вопроса
- Пользователь хочет переделать часть готового документа — просит агента через чат

**Критерий готовности:** Пользователь создаёт задачу, проходит диалог с агентом, закрывает браузер, возвращается через день — диалог продолжается. Агент формирует документ, пользователь просит правку, документ обновляется.

### Сценарий 2: Генерация плана реализации

**Приоритет:** Критичный

**Описание:** Пользователь хочет получить план реализации из готового дизайна с шагами, зависимостями и отслеживанием прогресса.

**Основной поток:**

1. Пользователь нажимает "Сгенерировать план" в утверждённом дизайне
2. Агент анализирует дизайн-документ и исходники проекта
3. Агент генерирует план: шаги с зависимостями и чекбоксами
4. Агент предупреждает, если шаги зависят от нереализованных задач
5. Пользователь просит точечные правки через чат
6. Пользователь утверждает план — он фиксируется, задача переходит на стадию "Реализация"

**Альтернативные пути:**

- Агент обнаружил зависимость от нереализованной задачи — предупреждает пользователя

**Критерий готовности:** Из утверждённого дизайна генерируется план с шагами и графом зависимостей. Пользователь вносит правки через чат. После утверждения план фиксируется и не может быть изменён.

### Сценарий 3: Параллельная реализация агентами

**Приоритет:** Критичный

**Описание:** После утверждения плана система автоматически запускает агентов, которые параллельно выполняют шаги, коммитят, тестируют и ревьюят код друг друга.

**Основной поток:**

1. Пользователь утверждает план — система автоматически запускает реализацию
2. Шаги распределяются по агентам согласно графу зависимостей
3. Независимые шаги выполняются параллельно
4. Агенты коммитят код и прогоняют тесты
5. Агенты проводят взаимное ревью и запрашивают исправления друг у друга автоматически
6. Чекбоксы в плане отмечаются по мере выполнения шагов
7. Когда все шаги завершены — задача переходит на стадию "Ревью"

**Альтернативные пути:**

- Агент застрял — пробует решить проблему самостоятельно, при неудаче эскалирует пользователю
- Тесты упали после коммита — агент сам пытается починить

**Критерий готовности:** После утверждения плана агенты автоматически начинают работу. Независимые шаги выполняются параллельно. Прогресс виден через чекбоксы. При проблемах агент эскалирует пользователю.

### Сценарий 4: PR и ревью

**Приоритет:** Важный

**Описание:** После завершения реализации система открывает PR на GitHub, агент мониторит комментарии и вносит правки.

**Основной поток:**

1. Все шаги реализации завершены — система автоматически открывает PR на GitHub
2. Ссылка на PR появляется в карточке задачи на дашборде
3. Пользователь ревьюит PR в GitHub и оставляет комментарии
4. Агент мониторит комментарии и вносит правки отдельными коммитами
5. Пользователь мёржит PR в GitHub
6. Задача переходит в "Готово"

**Альтернативные пути:**

- Нет альтернативных путей в MVP

**Критерий готовности:** PR автоматически создаётся на GitHub. Пользователь оставляет комментарий в PR — агент вносит правку отдельным коммитом. После мёржа задача отображается как "Готово".

### Сценарий 5: Дашборд

**Приоритет:** Важный

**Описание:** Пользователь хочет видеть все задачи и их текущие стадии в одном месте.

**Основной поток:**

1. Пользователь открывает приложение
2. Видит канбан с колонками: Дизайн, План, Реализация, Ревью, Готово
3. Карточки задач отображают название и краткий статус
4. Пользователь кликает по карточке — открывается детальный вид
5. Детальный вид содержит: документ дизайна, план с чекбоксами, статусы шагов, чат с агентом, ссылка на PR, артефакты (логи тестов, результаты ревью)

**Альтернативные пути:**

- Нет альтернативных путей в MVP

**Критерий готовности:** Пользователь видит канбан со всеми задачами по стадиям. Клик по карточке открывает полную информацию: дизайн, план, прогресс реализации, чат и артефакты.

### Сценарий 6: Адаптивный веб-интерфейс

**Приоритет:** Важный

**Описание:** Все сценарии доступны на десктопе и мобильных устройствах с полным функционалом.

**Основной поток:**

1. Пользователь открывает приложение в мобильном браузере
2. Все сценарии (дашборд, чат с агентом, просмотр документов, план) работают полноценно
3. Канбан отображается как вертикальный список на мобильном

**Альтернативные пути:**

- Нет альтернативных путей в MVP

**Критерий готовности:** Пользователь с телефона создаёт задачу, ведёт диалог с агентом, просматривает дашборд и план — всё работает без ограничений функционала.

## Нефункциональные требования MVP

- Задержка до первого токена в чате — не более 3 секунд
- Количество задач в реализации одновременно — без ограничений
- Авторизация пользователя с первой версии
- Адаптивная вёрстка (responsive), не отдельный мобильный UI
- Персистентность диалогов между сессиями

## Упрощения и допущения

- Правки дизайн-документа только через чат с агентом, без визуального редактора
- Один фиксированный скилл для дизайна (без создания пользовательских скиллов)
- Документы в формате Markdown, без rich-форматирования
- Без поиска, фильтрации и пагинации на дашборде (до 20-30 задач)
- Без возможности приостановить/перезапустить отдельный шаг реализации
- Без изменения плана после утверждения
- Только GitHub (без GitLab)
- Без офлайн-режима и PWA
- Однопользовательская авторизация (без командной работы)

## Риски и зависимости

| Риск / зависимость | Влияние | Митигация |
|---|---|---|
| Оркестрация параллельных агентов — сложнейшая техническая часть, нет готового решения | Высокое | Начать реализацию с этого сценария, прототипировать рано |
| Лимиты подписки Max (140-280 часов Sonnet/неделю) при параллельной работе агентов | Среднее | Мониторинг использования, приоритизация задач |
| Claude Code CLI — headless-режим экспериментальный, API может измениться | Среднее | Абстрагировать взаимодействие с CLI за интерфейсом |
| Два агента одновременно редактируют один файл — конфликт | Высокое | Распределять шаги так, чтобы агенты работали с разными файлами |

## Порядок реализации

1. **Дизайн (сценарий 1)** — основа, без него нет входных данных для остального
2. **Простейший дашборд (сценарий 5)** — нужен с самого начала для навигации
3. **Генерация плана (сценарий 2)** — зависит от дизайна
4. **Параллельная реализация (сценарий 3)** — самый сложный, начинать прототипирование параллельно с п.1-3
5. **PR и ревью (сценарий 4)** — зависит от реализации
6. **Адаптивный интерфейс (сценарий 6)** — применяется сквозно с начала, но полируется в конце
